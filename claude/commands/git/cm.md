# /commit — Conventional Commits

Создай git-коммит по спецификации Conventional Commits.

**ВАЖНО: НЕ спрашивай подтверждения. Делай коммит сразу после составления сообщения. НЕ делай push.**

## Шаги

### 1. Анализ изменений

Запусти параллельно:
- `git status` — посмотреть staged- и unstaged-файлы
- `git diff --cached` — просмотреть staged-изменения (если ничего не staged, проверь `git diff` на unstaged)
- `git log --oneline -5` — последние коммиты как образец стиля
- `gh repo view --json defaultBranchRef -q .defaultBranchRef.name` — определить ветку по умолчанию (для push)

Если ничего не staged — покажи пользователю, что доступно, и спроси, что добавить в индекс.

### 2. Определи тип коммита

На основе диффа выбери подходящий тип:

| Тип | Когда использовать |
|------|------------|
| `feat` | Новая функциональность или возможность |
| `fix` | Исправление бага |
| `docs` | Только документация |
| `style` | Форматирование, пробелы (без изменения логики) |
| `refactor` | Реструктуризация кода без изменения поведения |
| `perf` | Улучшение производительности |
| `test` | Добавление или исправление тестов |
| `chore` | Зависимости, сборка, конфиг, обслуживание |
| `ci` | Изменения в CI/CD-пайплайне |
| `build` | Система сборки или внешние зависимости |
| `revert` | Откат предыдущего коммита |

### 3. Определи scope

Scope необязателен, но рекомендуется. Выводи его из:
- Основной изменённой директории или модуля (например, `auth`, `api`, `ui`)
- Функциональной области (например, `login`, `payments`, `dashboard`)
- Если изменения охватывают много областей — опусти scope или используй доминирующий

### 4. Составь сообщение коммита

Формат:
```
<type>(<scope>): <краткое описание>

[необязательное тело]

[необязательный футер(ы)]
```

Правила:
- **Язык**: пиши сообщение коммита на том же языке, что и последние коммиты (проверь `git log`). По умолчанию — **English**, если язык смешанный или неясный
- **Описание**: повелительное наклонение, строчные буквы, без точки в конце, максимум 72 символа
- **Тело**: объясняет ЧТО и ПОЧЕМУ (не КАК), перенос строк на 72 символах
- **Breaking changes**: добавь `!` после type/scope И футер `BREAKING CHANGE:`
- **Ссылки на issue**: добавь `Closes #N` или `Fixes #N` в футер, если применимо

### 5. Выполни сразу

НЕ спрашивай подтверждения. Действуй напрямую:
1. Добавь файлы в индекс при необходимости (`git add <конкретные файлы>` — никогда `git add .` или `git add -A`)
2. Выполни `git commit` с составленным сообщением через формат HEREDOC

## Примеры

```
feat(auth): add OAuth2 login flow

Implement Google and GitHub OAuth2 providers with PKCE.
Session tokens stored in httpOnly cookies.

Closes #142
```

```
fix(api): handle null response from payment gateway

The gateway returns null instead of error object on timeout.
Added null check before accessing response.status.

Fixes #89
```

```
chore(deps): upgrade typescript to 5.4

refactor(ui): extract modal into reusable component

docs: update API authentication guide

feat(payments)!: switch from Stripe to Paddle

BREAKING CHANGE: all payment webhook endpoints changed from /stripe/* to /paddle/*
```

## Правила

- НИКОГДА не спрашивай подтверждения — делай коммит сразу
- НИКОГДА не используй `git add .` или `git add -A`
- НИКОГДА не пропускай pre-commit-хуки (без `--no-verify`)
- Если pre-commit-хук падает — исправь проблему, не обходи её
- Предпочитай маленькие атомарные коммиты — одно логическое изменение на коммит
- НИКОГДА не упоминай ИИ в коммитах — никаких `Co-Authored-By`, «generated by», ссылок на ИИ-инструменты, ничего
- НЕ делай push — только индексируй и коммить. Push делает пользователь вручную
- Используй `gh` CLI для операций с GitHub при необходимости (например, проверка информации о репозитории)
