# /pr — Создание Pull Request

Создай pull request через `gh` CLI с заголовком в стиле Conventional Commits и аккуратным описанием.

**ВАЖНО: НЕ запускай автоматически. Дождись подтверждения пользователя перед выполнением `gh pr create`.**

## Переменные

- `TARGET_BRANCH`: `$1` (по умолчанию `main`)
- `SOURCE_BRANCH`: текущая ветка (`git branch --show-current`)

## Шаги

### 1. Собери контекст

Запусти параллельно:
- `git branch --show-current` — получить имя исходной ветки
- `git log --oneline $(git merge-base HEAD $TARGET_BRANCH)..HEAD` — коммиты с момента расхождения с целевой веткой
- `git diff $(git merge-base HEAD $TARGET_BRANCH)..HEAD --stat` — сводка изменённых файлов
- `git diff $(git merge-base HEAD $TARGET_BRANCH)..HEAD` — полный дифф для понимания изменений
- `gh pr list --head $(git branch --show-current) --json number,state -q '.[0]'` — проверить, существует ли PR уже

Если PR уже существует — сообщи пользователю и остановись.

Если исходная ветка совпадает с целевой — предупреди и остановись.

### 2. Составь заголовок PR

Используй формат Conventional Commits для заголовка:

```
<type>(<scope>): <краткое описание>
```

- Те же правила типов, что и для коммитов: `feat`, `fix`, `refactor`, `chore`, `docs` и т.д.
- Повелительное наклонение, строчные буквы, без точки, максимум 72 символа
- Выводи type и scope из реальных изменений, а не из догадок по имени ветки

### 3. Составь описание PR

**Язык**: пиши заголовок и описание по умолчанию на **English**. Используй другой язык, только если пользователь явно попросил (например, «pr на русском», «описание на русском»). Язык последних коммитов/PR — НЕ сигнал: по умолчанию остаётся English, пока явно не сказано иное.

Напиши аккуратное, читаемое человеком описание:

```markdown
## Обзор

Краткое объяснение того, что делает этот PR и почему (2–4 предложения максимум).

## Изменения

- Список ключевых изменений
- Фокус на ЧТО и ПОЧЕМУ, а не КАК
- Логически группируй связанные изменения

## Заметки

Любой дополнительный контекст: шаги миграции, breaking changes, зависимости, на что обратить внимание при ревью.
```

Правила для описания:
- Будь кратким и конкретным — без воды и филлеров
- Полностью опусти раздел `## Заметки`, если отмечать нечего
- **НЕ добавляй раздел `## Test plan` / `## Tests` / `## Testing` / `## QA` ни при каких обстоятельствах.** Никогда не включай чек-листы тестов, шаги ручного QA или заметки о покрытии тестами. Тесты живут в диффе, а не в описании PR. Это правило абсолютно — не добавляй его, даже если в диффе есть тесты, даже если пользователь просил тщательности, даже если шаблон это предлагает.
- **НИКОГДА не добавляй футер, подпись, атрибуцию или строку «Generated with».** Никаких `🤖 Generated with [Claude Code]`, никаких `Co-Authored-By`, никаких ссылок на Anthropic, никаких эмодзи, указывающих на ИИ-авторство. Тело PR должно заканчиваться последней строкой реального содержимого.
- НИКОГДА не упоминай ИИ, LLM, ассистентов, копайлотов, Claude, ChatGPT, «generated by» или любой ИИ-инструментарий — ни в заголовке, ни в описании, ни в футере
- Пиши так, будто разработчик написал всё сам

### 4. Покажи пользователю для подтверждения

Покажи предлагаемые:
- **Source** → **Target** ветка
- **Заголовок**
- **Описание** (отформатированное)

Попроси пользователя подтвердить или отредактировать.

### 5. Выполни

Только после подтверждения пользователя:

```bash
gh pr create \
  --base <TARGET_BRANCH> \
  --head <SOURCE_BRANCH> \
  --title "<title>" \
  --body "<description>"
```

После создания покажи URL PR.

## Правила

- НИКОГДА не создавай PR без подтверждения пользователя
- НИКОГДА не упоминай ИИ, LLM, Claude, ChatGPT, копайлотов или любой ИИ-инструментарий — нигде в заголовке, описании или футере
- НИКОГДА не добавляй футер/подпись/«Generated with»/`Co-Authored-By` — тело заканчивается реальным содержимым
- НИКОГДА не добавляй раздел «Test plan» / «Tests» / «Testing» / «QA» в описание, никогда
- Язык по умолчанию — English; переключайся только по явному запросу пользователя
- НИКОГДА не делай push ветки — если upstream отсутствует, предупреди пользователя сделать push сначала
- Используй `gh` CLI для всех операций с GitHub
- Если нет коммитов впереди целевой ветки — предупреди и остановись
